# How a Build Works

Vidar never makes machine code. Every command does the same first step: it reads your program, checks it, and writes it out again as plain Odin. Then it runs the `odin` compiler on the result.

```text
main.vidar ──vidar──▶ main.odin ──odin──▶ executable
```

Let's look at that Odin. `vidar emit` prints it:

```console
$ vidar emit hello
```

For Listing 1-3, it prints this (shortened):

```odin
package main; import __vidar "vidar_runtime"

import "core:fmt"

main :: proc() {
	name := "world"
	greet := __closure_0(name)
	greet.call(greet.env, "Hello")
	greet.call(greet.env, "Goodbye")
}

// ---- generated by vidar ----

__closure_0 :: proc(__c0: $T0) -> __vidar.Closure(proc(__vidar.Env, string)) {
	...
		call = proc(__env_raw: __vidar.Env, greeting: string) { __env := transmute(__Env)__env_raw; fmt.printfln("%s, %s!", greeting, __env.name) },
	...
}
```

Three things are worth noticing.

**Most lines didn't change.** Only the lines with something new on them were rewritten: the closure became a call to a generated constructor, `__closure_0(name)`, and calling it became `greet.call(greet.env, ...)`. Everything else, including comments, blank lines and formatting, comes out exactly as you wrote it. An Odin file that uses nothing from Vidar comes out byte for byte the same.

**Every line can be traced back.** The code a construct needs elsewhere, such as the closure's body, goes at the end of the file, after the `generated by vidar` line, and Vidar keeps a map from each generated line to the line of yours it came from. The body's `fmt.printfln` maps back to line 8 of `main.vidar`, where you wrote it. So an error that Odin reports in the generated code points at the right line of your `.vidar` file, and `vidar` rewrites the file name and line for you.

**Generated names start with `__`.** `__closure_0`, `__vidar`, `__env`: anything Vidar invents starts with two underscores, so it can't clash with your names. The editor hides these names from completion.

## The Commands

| Command | What it does |
|---|---|
| `vidar run <dir>` | transpiles into a temporary directory, then `odin run` |
| `vidar check <dir>` | transpiles, then `odin check` |
| `vidar test <dir>` | transpiles, then `odin test` (see [Chapter 12](ch12-00-testing.md)) |
| `vidar build <dir>` | writes the generated Odin to `out/<name>` (or `-o <dir>`); `-bin` also builds it |
| `vidar emit <dir>` | prints the generated Odin |

Each command takes a directory (a package) or a single `.vidar` file. Packages that the program imports by relative path are transpiled with it, so `vidar build` writes a whole tree of packages. [The `vidar` Command](ch16-01-command-line.md) covers every command and flag.

## Errors at Your Lines

A mistake shows up at the line you wrote, whether Vidar finds it or Odin does. Vidar checks its own constructs first and reports problems with them directly. Anything else goes through to `odin`, and `vidar` rewrites the locations in Odin's messages from the generated `.odin` file to your `.vidar` file. Panics and failed assertions in a running program are rewritten the same way.

`vidar build` also writes `vidar.map.json` next to the generated code: the map from each generated line back to its source. When you run a binary you built yourself, `vidar map` uses that file to rewrite a crash log after the fact:

```console
$ ./out/hello/hello 2>&1 | vidar map out/hello
```

## Summary

You've installed Vidar, written and run a program, and seen what Vidar does with it: it writes plain Odin, changing only the lines that use something new and keeping every line where it was. In the next chapter, we'll take a quick tour of the Odin that the rest of this book is built on.
